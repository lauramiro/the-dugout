# The Dugout

F1 explains the pit wall. The NFL explains fourth down. Football's dugout is still a black box.

The Dugout explains a football manager's decisions as they happen: who is tiring, when a change is due, what each option is worth in win probability, and at full time what a different call would have changed. It is an entry to the Microsoft x Premier League "Inside the Game" developer hackathon.

## Pitch

A substitution is the biggest decision a manager makes during a match, and broadcasts explain it after the fact, if at all. The Dugout ingests a synthetic match event stream through Azure Event Hubs, turns it into what a real club could observe (score, clock, scoring rates, a condition estimate per player, threat by channel), and opens a decision card when a change becomes worth discussing. A Monte Carlo engine prices each option (no change, like-for-like, tactical) as a change in win probability with an interval and a strength label. Narration agents built with Microsoft Agent Framework on a Microsoft Foundry model deployment write the card for a casual fan or an analyst, and a code check verifies every number before it reaches the screen. Cards reach the page over Azure Web PubSub; the decision service and the live pipeline run on Azure Container Apps; the page is on Azure Static Web Apps. Fans vote on the call before the reveal, and at full time a recap shows what each decision was worth.

Because the match is simulated, the engine can be graded against the truth: at every decision point the simulator is forked and both options are played out, which real football can never offer ([evaluation](docs/evaluation.md)).

## Synthetic data statement

Every match in this repository is generated by our own simulator. There is no real Premier League data, and no real club, player or league names or logos. Riverside FC, Castleton Athletic and their players are fictional. Nothing here is betting-related.

The demo story (a tiring left-back, an equaliser down his flank, a late substitution) is picked from honest simulation runs by a seed search, not written by hand.

## How it maps to the challenge

| Stage | What The Dugout does | Code |
| --- | --- | --- |
| Ingest | A one-second-tick possession simulator emits passes, shots, tackles, possession changes, pressure, runs, substitutions and match metadata, plus 2 Hz tracking frames. The replayer sends a recorded match into Event Hubs; the live runner consumes it as it arrives. | `dugout/sim/`, `dugout/stream/replay.py`, `dugout/stream/consumer.py` |
| Interpret | The state engine builds a snapshot every 10 s: score, clock, substitutions left, rolling xG rates blended with a prior, a condition estimate per player from running load and recent minutes, and threat by channel. | `dugout/stream/state_engine.py` |
| Explain | Triggers open a card when a player's condition drops, after a late goal, or on a substitution. The decision engine prices each option as a change in win probability, with a 90% interval and a strength label (strong, lean, toss-up), and the card says why. | `dugout/stream/triggers.py`, `dugout/engine/` |
| Render | Machine-readable cards and snapshots (four documented contracts) drive an SVG pitch, win-probability timeline with decision markers, a dugout panel with condition bars, and the decision card. | `docs/data-contracts.md`, `web/` |
| Personalize | Casual view (plain words, whole numbers) or analyst view (one decimal and the interval); English or Spanish, for the screen, the cards and the recap; choice of club, which reorders the panel and flips the timeline; "Your call" vote with a 20-second timer; full-time review with recap lines per mode. | `web/components/`, `dugout/agents/` |

## Architecture

```
simulator -> replayer -> Azure Event Hubs -> pipeline runner (Container Apps)
                                              state engine -> triggers
                                              -> decision service (Container Apps)
                                                 engine -> narration workflow (Agent Framework + Foundry)
                                              -> Azure Web PubSub -> web page (Static Web Apps)
```

### Agents

Narration is a Microsoft Agent Framework workflow (`dugout/agents/workflow.py`): narrator -> grounding check -> localizer -> grounding check. The narrator writes analyst text in English from the engine's payload; the localizer translates it to the viewer's language (English or Spanish, with Spanish decimal commas) and adjusts it for the viewer's mode. Each check is plain code (`dugout/agents/grounding.py`): every number must match a payload field, every player id must exist in the payload, the strength word must match the recommendation, no internal name may leak, and the word limits hold. A failed check sends the stage back once with the errors attached; a timeout, model error or second failure ends in a template that passes the check by construction, so the screen never waits on or trusts the model. A recap writer (`dugout/agents/recap.py`) writes the full-time lines under the same check, plus a filter on blame and hindsight words.

Measured on 100 cards with the deployed gpt-5-mini model: 84% shown from the model, 85.8% of replies grounded on the first attempt, median 3.15 s per card ([narration eval](eval/results/narration.md)).

### MCP server

The decision service also serves a Model Context Protocol server at `/mcp` (`dugout/service/mcp_server.py`; Streamable HTTP, stateless, so it scales with the Container App). Any MCP client, such as GitHub Copilot agent mode, a Foundry agent or Claude, can work with the match through four read-only tools:

| Tool | What it returns |
| --- | --- |
| `match_overview` | Clubs, final score, goals, substitutions and every decision point the triggers raised |
| `match_state` | What a club could observe at a minute: score, substitutions left, scoring rates, each player's condition estimate |
| `price_options` | The decision engine at any minute, for either team: every option's win probability and expected points, the gap to no change with a 90% interval, the recommendation and its strength |
| `explain_decision` | A narrated card in English or Spanish, casual or analyst, written by the narration workflow and passed by the grounding check |

The tools call the same state engine, decision engine and narration workflow as the live screen, so an agent gets the same numbers and the same checked text a viewer does. A producer can ask "what was the left-back change worth at 64'?" and get the engine's answer, not a model's guess.

To connect GitHub Copilot in VS Code, add `.vscode/mcp.json`:

```json
{ "servers": { "the-dugout": { "type": "http", "url": "https://dugout-service.wittypond-73564413.northeurope.azurecontainerapps.io/mcp" } } }
```

Claude Code: `claude mcp add --transport http the-dugout https://dugout-service.wittypond-73564413.northeurope.azurecontainerapps.io/mcp`

## Microsoft technology

- **Microsoft Foundry:** model deployment for the narration and recap agents (`infra/foundry.sh`, `dugout/agents/foundry.py`).
- **Microsoft Agent Framework:** the narration workflow with grounding checks and retries (`dugout/agents/workflow.py`).
- **Azure Event Hubs:** match event ingestion (`dugout/stream/replay.py`, `dugout/stream/consumer.py`).
- **Azure Container Apps:** the decision service (with its MCP server) and the live pipeline runner, two apps from one image (`Dockerfile`, `infra/deploy.sh`).
- **Azure Web PubSub:** cards, snapshots and events pushed to the page (`dugout/service/publisher.py`, `web/lib/live.ts`).
- **Azure Static Web Apps:** the web page (`web/`, `infra/deploy.sh`).

## Results

The counterfactual check compares the engine's estimated gap with the true simulated gap at 149 decision points over 31 seeds, calibrating three constants on the fit seeds and reporting on held-out seeds. On the test set the correlation is 0.72, mean error -0.12 points, and sign agreement 75.7%. The limits are stated in full in [docs/evaluation.md](docs/evaluation.md).

## Run it

Requires [uv](https://docs.astral.sh/uv/) and Node.js.

```
uv sync
uv run pytest
uv run python -m dugout.sim run --seed 1 --out data/rfc-cas-0001.jsonl
uv run python -m dugout.stream.pipeline data/demo-rfc-cas-0073.jsonl --scenario scenarios/riverside-castleton.yaml
uv run uvicorn dugout.service.app:app --port 8000   # MCP at http://localhost:8000/mcp

cd web && npm install && npm run dev
```

The page replays the demo match from `web/public/demo/` by default; open it with `?source=live` to follow the Web PubSub feed. Without `FOUNDRY_ENDPOINT` (see `env.example`) narration uses the templates. To deploy to Azure, run `infra/foundry.sh` and then `infra/deploy.sh`; both print every command and change nothing without `--apply`.
