# The Dugout

F1 explains the pit wall. The NFL explains fourth down. Football's dugout is still a black box.

The Dugout explains a football manager's decisions as they happen: who is tiring, when a change is due, what each option is worth in win probability, and at full time what a different call would have changed. It is an entry to the Microsoft x Premier League "Inside the Game" developer hackathon.

Decision service: https://dugout-service.wittypond-73564413.northeurope.azurecontainerapps.io/healthz (says what it runs on: Foundry or templates, the model, Web PubSub, MCP). ## Pitch

A substitution is the biggest decision a manager makes during a match, and broadcasts explain it after the fact, if at all. The Dugout ingests a synthetic match event stream through Azure Event Hubs, turns it into what a real club could observe (score, clock, scoring rates, a condition estimate per player, threat by channel), and opens a decision card when a change becomes worth discussing. A Monte Carlo engine prices each option (no change, like-for-like, tactical) as a change in win probability with an interval and a strength label. Narration agents built with Microsoft Agent Framework on a Microsoft Foundry model deployment write the card for a casual fan or an analyst, and a code check verifies every number before it reaches the screen. Cards reach the page over Azure Web PubSub; the decision service and the live pipeline run on Azure Container Apps; the page is on Azure Static Web Apps. Fans vote on the call before the reveal, and at full time a recap shows what each decision was worth.

Because the match is simulated, the engine can be graded against the truth: at every decision point the simulator is forked and both options are played out, which real football can never offer ([evaluation](docs/evaluation.md)).

## Synthetic data statement

Every match in this repository is generated by our own simulator. There is no real Premier League data, and no real club, player or league names or logos. Riverside FC, Castleton Athletic and their players are fictional. Nothing here is betting-related.

The demo story (a tiring left-back, an equaliser down his flank, a late substitution) is picked from honest simulation runs by a seed search, not written by hand.

| Render | Broadcast mode: the match full-bleed in a 16:9 picture with timed graphics (scorebug, decision lower third, fading-player tag, win-probability worm, goal flash, manager's call, full-time What if), all played from an exportable cue sheet. | Personalize | Casual view (plain words, whole numbers) or analyst view (one decimal and the interval); English or Spanish, for the screen, the cards and the recap; favourite club (broadcast: the worm follows that club); player focus (broadcast: a tag follows the player all match and their events get a card); "Your call" vote with a 20-second timer; a fan view (`/fan`) that shows one club's card with what the manager is weighing (who is fading, why now, the options, who is on the bench) before the vote; full-time review with recap lines per mode. | `web/components/`, `dugout/agents/` |

## The guided story

A first visit to `/` offers a guided story of a little over a minute: the 60' decision on the demo match, seen three ways. On TV, the match plays from just before 60' until the model flags Leon Varga; the view moves into the manager's tablet, which is the analyst desk itself with Varga picked out; then into the fan's phone, where the viewer votes with the same information; the equaliser down Varga's flank and the manager's change at 79' follow, with the viewer's call beside the manager's and the model's, and full time ends on the What if for that decision. Every screen is the running app, not a recording: the story only picks the minute, cuts between screens and adds a caption. Captions are built from the match data (`web/lib/story.ts`), so a rebuild of the demo files keeps their names and minutes right; the guide itself is a tested state machine (`web/lib/storyPlayer.ts`). Pause, Next and Leave are always on screen; the page's own Play and Pause pause and resume the story, while seeking (a chapter, the timeline) or changing speed leaves it. Leaving from the tablet or the phone opens `/desk` or `/fan` at the same moment, club and language; votes cast during the story stay with the story. A link with `?t=` skips the story.

## Broadcast mode

The landing page `/` is the TV picture (`/broadcast` still works). The match fills a 16:9 stage, drawn from the 2 Hz tracking data, and The Dugout appears as broadcast graphics that come in when they matter and go out on their own: a scorebug; a lower third when a decision card opens (trigger, strength, the model's line in the viewer's language and mode, the options as win-probability bars); a condition ring on the fading player; a win-probability worm along the bottom; a goal strip; the manager's call; and at full time a "What if" segment led by the decision with the largest gap, with a **Match report** tab beside it (replay only): the result, the goals and the decision of the match, built from the match data and the review's own checked line, with **Copy for the studio** and the cue sheet for the gallery. Players are tagged in real time when they cross a threshold: a sprint of 30 m or more (about the longest tenth) shows its distance, and any player above 8 m/s (28.8 km/h) shows their speed from the tracking frame; both tags step aside while a decision card is over the picture (the phone layout keeps them). Every 15 minutes and at half-time a stats graphic shows passing and running, for both teams or for the player the viewer follows: passes, share played forward, average and longest pass (measured from each pass's start and end points), sprints, longest sprint and fast-running distance. Pass accuracy is not shown: the simulator records completed passes only (a lost ball is a duel won by the defender), so every pass would read 100%. A strip under the scorebug and another under the settings chip name each club's bench (the players who have not played yet) with subs and windows left. **Under the hood** (top bar) shows the architecture, what each Azure service does, the agent chain and how to connect an MCP client. Settings (top right) choose casual or analyst, English or Spanish, a favourite club and a player to follow, and link to the analyst desk at `/desk`.

Every graphic is a cue on one timeline, built by a pure function from the match log (`web/lib/cues.ts`, tested with `npm test` in `web/`). The cue sheet is the machine-readable output a production graphics system would play: **Export cue sheet** in the settings downloads it, and `/?cues=json` shows it.

Live (`?source=live`) the same graphics come from the Web PubSub feed (if the connection drops, the page keeps the match on screen, negotiates a fresh URL and reconnects, waiting 1 s and doubling up to 30 s between tries): the runner adds match events (goals, substitutions, shots, fouls, cards, passes, sprints and fast runs, without their empty fields) and one win-probability point per minute to the snapshots and cards. Tracking frames stay off the feed (it was sized for the Web PubSub Free tier the project started on); when the live match is the recorded demo match, the picture draws the recorded tracking at the live clock and the settings say "Recorded tracking". Live cards carry no manager action or review, so live the manager's call appears only when a change closes a card that is still open, shows who came off and on without the verdict, and the What if segment is replay only. In the demo match every card closes after its three minutes, before the manager acts, so live shows no manager's call; the replay shows each one.

## Architecture

![The Dugout on Azure: a replayer sends match events to Event Hubs; the pipeline runner on Container Apps reads them, narrates through Microsoft Foundry and publishes to Web PubSub; the browser loads the page from Static Web Apps and gets cards over WebSocket; the decision service on Container Apps hands out WebSocket URLs, counts votes and serves MCP clients](docs/architecture.png)

Source: [`docs/architecture.mmd`](docs/architecture.mmd) (Mermaid; an editable [Excalidraw](docs/architecture.excalidraw) and an [SVG](docs/architecture.svg) sit beside it).

1. The replayer sends a recorded match into **Azure Event Hubs**, at match speed or faster.
2. The **pipeline runner** (Azure Container Apps) reads the events as they arrive and runs the whole chain in process: state engine, triggers, decision engine, then the narration workflow, which calls the **Microsoft Foundry** model deployment.
3. The runner publishes cards (all four language and mode versions), slimmed snapshots, key match events and a win-probability point per minute to **Azure Web PubSub**.
4. The page, a static export on **Azure Static Web Apps**, asks the **decision service** (Container Apps) for a short-lived WebSocket URL (`/negotiate`) and follows the feed. Without `?source=live` it replays the recorded match from its own files, with no backend at all.
5. The decision service also counts "Your call" votes and serves the MCP tools, which call the same engine and narration workflow.

### Agents

Narration is a Microsoft Agent Framework workflow (`dugout/agents/workflow.py`): narrator -> grounding check -> localizer -> grounding check. The narrator writes analyst text in English from the engine's payload; the localizer translates it to the viewer's language (English or Spanish, with Spanish decimal commas) and adjusts it for the viewer's mode. Each check is plain code (`dugout/agents/grounding.py`): every number must match a payload field, every player id must exist in the payload, the strength word must match the recommendation, no internal name may leak, and the word limits hold. A failed check sends the stage back once with the errors attached; a timeout, model error or second failure ends in a template that passes the check by construction, so the screen never waits on or trusts the model. A recap writer (`dugout/agents/recap.py`) writes the full-time lines under the same check, plus a filter on blame and hindsight words. Every card keeps a trace of its steps (each draft, what the check said, any retry or template), and **How this line was written** on the TV's decision card shows it, so a viewer can see the agents and the check at work on that very line.

Measured on 100 cards with the deployed gpt-5-mini model (2026-10-26, after the stricter checks of 25 October): 83% shown from the model, 80.6% of replies grounded on the first attempt, 20 of 36 retries passed, median 3.14 s per card; a repeat run gave 73%, so expect roughly 73% to 83% ([narration eval](eval/results/narration.md)). In Spanish, 88% shown from the model and 84.3% grounded on the first attempt ([Spanish run](eval/results/narration-es.md)). The check also rejects English left in Spanish, a wrong article, a strong card called close, decimals or the interval in casual text, the gap called "expected points", a headline that takes a player off when the pick is another option, long dashes, and a strength word said twice; most of the remaining failures are casual lines that keep a decimal and toss-up cards whose headline still calls for an action.

### MCP server

The decision service also serves a Model Context Protocol server at `/mcp` (`dugout/service/mcp_server.py`; Streamable HTTP, stateless, so it scales with the Container App). Any MCP client, such as GitHub Copilot agent mode, a Foundry agent or Claude, can work with the match through four read-only tools:

| Tool | What it returns |
| --- | --- |
| `match_overview` | Clubs, final score, goals, substitutions and every decision point the triggers raised |
| `match_state` | What a club could observe at a minute: score, substitutions left, scoring rates, each player's condition estimate |
| `price_options` | The decision engine at any minute, for either team: every option's win probability and expected points, the gap to no change with a 90% interval, the recommendation and its strength |
| `explain_decision` | A narrated card in English or Spanish, casual or analyst, written by the narration workflow and passed by the grounding check |

`explain_decision` and `price_options` also carry an MCP App (the `io.modelcontextprotocol/ui` extension, spec 2026-01-26): a host that supports MCP Apps renders the decision card itself next to the answer (for `price_options`, the options without narration) (`ui://the-dugout/decision-card.html`, in the viewer's language and light or dark theme), while other clients get the same JSON as before.

The tools call the same state engine, decision engine and narration workflow as the live screen, so an agent gets the same numbers and the same checked text a viewer does. A producer can ask "what was the left-back change worth at 64'?" and get the engine's answer, not a model's guess.

To connect GitHub Copilot in VS Code, add `.vscode/mcp.json`:

```json
{ "servers": { "the-dugout": { "type": "http", "url": "https://dugout-service.wittypond-73564413.northeurope.azurecontainerapps.io/mcp" } } }
```

Claude Code: `claude mcp add --transport http the-dugout https://dugout-service.wittypond-73564413.northeurope.azurecontainerapps.io/mcp`

The page also serves [`/llms.txt`](https://ashy-ocean-03bdf100f.2.azurestaticapps.net/llms.txt) (the llmstxt.org format), so an agent that lands on the site finds the MCP server and the docs without scraping the page.

## Built on Azure

| Service | Role in The Dugout | Configuration |
| --- | --- | --- |
| **Azure Event Hubs** | Ingest: the match event stream, decoupled from whoever consumes it | Hub `matchevents`, Basic tier, 2 partitions, 24 h retention |
| **Azure Container Apps** | Compute: the live pipeline runner and the decision service, two apps from one image | Runner: 1 replica, no ingress, its own start command. Service: external HTTPS ingress, scales 0 to 10 replicas (`SERVICE_MIN_REPLICAS=1` in the deploy script keeps one warm, so the first request after a quiet spell does not wait for a cold start). 0.5 vCPU, 1 GiB each |
| **Azure Container Registry** | The one image both apps run, built in Azure from the repo's `Dockerfile` by `az containerapp up` | Basic; each app pulls with its system-assigned managed identity, no registry password |
| **Microsoft Foundry** | The model behind the narration and recap agents | `gpt-5-mini` (2025-08-07), Global Standard, minimal reasoning effort, uksouth |
| **Microsoft Agent Framework** | The narration workflow: narrator, grounding check, localizer, grounding check, with retries | `dugout/agents/workflow.py` |
| **Azure Web PubSub** | Push: cards, snapshots, events and win probability to every open page | Hub `decisions`, Standard tier (one unit, Standard_S1, for the judging days; `WPS_SKU` in the deploy script, Free_F1 by default); the browser gets a short-lived client URL from `/negotiate` |
| **Azure Static Web Apps** | The page: a Next.js static export, so it needs no server of its own | Free tier; `web/public/staticwebapp.config.json` sends a content security policy (scripts and styles from the page itself, connections only to Container Apps and Web PubSub), `nosniff`, a referrer policy and a permissions policy |
| **Cost Management** | A budget on the resource group | $40 a month (set at deploy with `BUDGET_USD`; the script default is $20), email alerts at 80% and 100% |

**One script, repeatable.** `infra/foundry.sh` and `infra/deploy.sh` create everything above. Both print every `az` command and change nothing without `--apply`, and every step is an upsert, so a rerun updates the running apps in place (about six minutes). Regions are North Europe for the apps, UK South for Foundry and East US 2 for Static Web Apps (the free subscription refused West Europe).

**Secrets.** Connection strings and the Foundry key are read into shell variables and stored as Container Apps secrets, referenced from environment variables with `secretref:`. They are never echoed, committed or written to disk, apart from the git-ignored local `.env` the replayer reads. `POST /decisions`, which publishes a card to every open page, is off unless `DECISIONS_TOKEN` is set and then needs it as a bearer token; the deployed runner opens decisions in process and never calls it. Vote ids are capped at 64 characters, since votes are held in memory.

**Built to keep going.** The screen never waits on the model: each model call has a 3 s timeout, and a timeout, a model error or a second failed grounding check falls back to a template that passes the check by construction. The runner catches a failed card or a failed publish (on the Free tier Web PubSub throttles with 429s), counts it and moves on, so one bad message never stops the match. On the last full live replay: full time reached, no failed publishes and no 429s.

**What would change for production.** Each limit is a deliberate cut for a hackathon budget:
- The runner keeps one replica, because Event Hubs has no checkpoint store here (a second replica would publish everything twice). A Blob Storage checkpoint store would allow more replicas and a restart without replaying the match.
- Votes live in the decision service's memory, so they reset when it scales to zero and are not shared across replicas. Azure Cosmos DB would hold them. The runner opens live cards in its own process, so the service counts a vote for any well-formed card id and one of the engine's options; the half-hourly replays reuse the same ids, so their votes add to the same tallies, and a viewer who votes again in a later replay replaces their earlier vote. The vote store is capped (5,000 cards, 50,000 votes each) and answers 503 when full.
- Event Hubs, Web PubSub and Foundry are reached with keys held as Container Apps secrets. The next step is Microsoft Entra ID role assignments for the apps' managed identities, as the image pull already does.
- Tracking frames stay off the live feed, as sized for the Free tier; the Standard unit it now runs on could carry them with a runner change.
- The MCP tools and the vote routes are public and not rate-limited; each `price_options` call runs up to 80,000 simulated matches. The replica cap (10) and the budget alert bound the cost; Azure API Management or Front Door rate limits would be the production answer.

## Results

The counterfactual check compares the engine's estimated gap with the true simulated gap at 149 decision points over 31 seeds, calibrating three constants on the fit seeds and reporting on held-out seeds. On the test set the correlation is 0.74, mean error +0.08 points, and sign agreement 78.4%. The limits are stated in full in [docs/evaluation.md](docs/evaluation.md).

## Run it

Requires [uv](https://docs.astral.sh/uv/) and Node.js.

```
uv sync
uv run pytest
uv run python -m dugout.sim run --seed 1 --out data/rfc-cas-0001.jsonl
uv run python -m dugout.stream.pipeline data/demo-rfc-cas-0073.jsonl --scenario scenarios/riverside-castleton.yaml
uv run uvicorn dugout.service.app:app --port 8000   # MCP at http://localhost:8000/mcp

cd web && npm install && npm run dev
```

GitHub Actions runs the same tests, the type check and the build on every push and pull request (`.github/workflows/ci.yml`), with no secrets.

The page replays the demo match from `web/public/demo/` by default; open it with `?source=live` to follow the Web PubSub feed. Without `FOUNDRY_ENDPOINT` (see `env.example`) narration uses the templates. To deploy to Azure, run `infra/foundry.sh` and then `infra/deploy.sh`; both print every command and change nothing without `--apply`.
